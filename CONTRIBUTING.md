# Участие в разработке

## Окружение

1. Поставьте [mise](https://mise.jdx.dev) и Docker.
2. `mise install` — Node.js, pnpm, gitleaks, lefthook, OpenTofu, osv-scanner. Версии закреплены в `mise.toml`.
3. `pnpm install`.
4. `pnpm dev:up` — локальные сервисы, роли PostgreSQL, миграции и git-хуки. Пароли и секреты для разработки генерируются в `.env` (не коммитится). Команду можно запускать повторно: недостающее добавится, существующее не изменится.
5. `pnpm dev:api` — собрать и запустить API на `http://127.0.0.1:3000`.

API подключается к базе двумя ролями, как в продакшене, — обе без прав суперпользователя и обхода RLS:

- `zvenko_app` — данные компаний, под политиками RLS;
- `zvenko_identity` — модуль входа: схема `identity` с хэшами паролей и сессиями. Роль приложения эту схему не видит, роль входа не видит данные компаний.

Миграции применяет роль-владелец схемы — отдельным шагом, не при старте API. В тестах это роль `zvenko_owner` без прав суперпользователя и обхода RLS — как владелец базы в Yandex Managed PostgreSQL. Суперпользователь в тестах (`admin`) только готовит данные и проверяет их в обход RLS. Локально `pnpm dev:up` пока применяет миграции суперпользователем контейнера: миграцию, которой нужны его права, остановят тесты в CI.

Есть только Docker? Подойдёт Dev Container — появится вместе с первыми приложениями.

**Безопасность установки зависимостей** (`pnpm-workspace.yaml`):

- новые версии пакетов ставятся только через 7 дней после публикации (карантин);
- при снижении уровня доверия к пакету установка падает;
- скрипты установки разрешаются явно, по одному пакету.

**Телеметрия Turborepo** отключена переменной в `mise.toml` и в CI.

## Новый адрес API

1. Права проверяются автоматически: без `@Public()` адрес доступен только сотруднику компании. Компания запроса — по адресу сайта (`neva.zvenko.ru`), а без поддомена — выбранная в сессии. Профиль доступа — аргумент `@Access()`, данные — только через `TenantDb`.
2. Добавьте адрес в реестр [`apps/api/test/isolation.test.ts`](apps/api/test/isolation.test.ts). Без записи тест упадёт, а по записи сгенерирует проверки: без входа — 401, чужой объект — 404, в списке нет чужих объектов.
3. `@Public()` — только осознанно (проверки здоровья, приём заявок с сайтов) и с записью `public` в реестре.
4. `@SessionOnly()` — для вошедшего пользователя без данных компании (выбор компании); в реестре — `session`, сессия — аргумент `@CurrentSession()`. Изоляцию такого адреса проверяют отдельные тесты рядом с ним.

## Журнал аудита

Важные действия (F-AUD-01: вход, 2FA, приглашения, роли, экспорт, настройки) пишутся в журнал компании через `AuditService.record`:

1. В той же транзакции `TenantDb`, что и действие, **последним шагом**: запись держит очередь журнала компании до конца транзакции.
2. Если действие выполняется вне этой БД, запись делается **до него**: без записи нет действия.
3. Новое действие — в `AUDIT_ACTIONS` с названием для интерфейса, в формате `раздел.действие`. Источник (IP, устройство, ID запроса) — аргумент `@RequestSource()`.
4. В подробностях (`details`) — без секретов и без лишних персональных данных.

Номер, время и цепочку хэшей ставит БД. Роль приложения может только дописывать содержимое записи. Изменить или удалить запись нельзя никому, включая владельца схемы, — это проверяют тесты.

**События входа** (Better Auth) модуль `identity` сообщает через порт `AuthEvents` из хуков в `identity/auth-hooks.ts`, пишет их `AuthAuditRecorder` (D30):

- вход и выход — в журнал компании, куда вошёл: по адресу сайта, а на общем адресе — выбранной в сессии. Вход без записи в журнал отменяется;
- неудачные попытки, блокировка, 2FA, пароль, завершение сессий — в журналы всех компаний пользователя. Пишутся в фоне: выход не блокируется, а время ответа на неудачный вход не выдаёт, есть ли такая почта.

## События

Изменение данных, на которое реагируют роботы, уведомления или вебхуки, публикует событие (F-EVT-01, ADR-0005):

1. `EventBus.publish(tx, tenantId, event)` — в той же транзакции `TenantDb`, что и изменение. Событие доставят, только если транзакция зафиксируется.
2. Подписчик реализует `EventSubscriber` и регистрируется в `EventSubscribers` при `onModuleInit`. Обработчик вызывается в транзакции компании события вместе с отметкой «обработано», поэтому повторная доставка не повторяет действие в БД. Внешние действия (вебхук, письмо) делайте идемпотентными по ID события.
3. Сбой обработчика — повтор с нарастающей паузой. После всех повторов событие уходит в мёртвую очередь `<подписчик>.dead`.

Очередь — pg-boss в схеме `pgboss`. Её ведёт только роль `zvenko_worker`: роль приложения пишет события в `outbox` своей компании, а в очередь их переносит диспетчер. Схему очереди ставит миграция. Если новая версия pg-boss меняет версию схемы, нужна новая миграция из `getMigrationPlans`: без неё фоновые задачи не запустятся («pg-boss database requires migrations»).

## Миграции с переносом данных

`FORCE ROW LEVEL SECURITY` скрывает строки компаний и от владельца таблицы. Поэтому миграция, которая переносит данные компаний, снимает его на время переноса и включает обратно в той же миграции. Перенос проверяется тестом: `startTestDatabase({ until })` применяет миграции до нужной, тест кладёт данные, затем применяет остальные — см. `packages/db/test/migrations.test.ts`.

## Как вносим изменения

**Ветки:** `main` защищена и меняется только через PR. Имена веток — `<тип>/<кратко>`, например `feat/deals-kanban`, `fix/webhook-signature`.

**Коммиты** — [Conventional Commits](https://www.conventionalcommits.org/ru/), описание по-русски:

```
feat(crm): канбан сделок
fix(channels): проверка подписи вебхука Telegram
```

Один коммит — одно логическое изменение. Сообщение проверяет commitlint в git-хуке.

**Git-хуки (lefthook)** перед коммитом проверяют секреты (gitleaks), формат и линт; перед push — типы. Хуки — удобство: всё то же самое проверяет CI.

**Windows:** коммитьте из Git Bash или PowerShell 7. Windows PowerShell 5.1 передаёт текст в git не в UTF-8 — кириллица в сообщении ломается, и commitlint отклоняет коммит.

**Ложное срабатывание gitleaks:** не отключайте правило. Пометьте конкретную строку комментарием `gitleaks:allow` с пояснением — исключение должно быть видно на ревью.

## Когда изменение «готово»

- [ ] Код и тесты; в описании PR — ID требований.
- [ ] Формат, линт, типы, тесты, сканеры безопасности — зелёные.
- [ ] Новые эндпоинты — с тестом изоляции компаний. Новые таблицы — с `tenant_id` и политиками RLS.
- [ ] Важные действия (F-AUD-01) записываются в журнал аудита.
- [ ] Бюджеты скорости не просели.
- [ ] Нет секретов. Для новой зависимости объяснено, зачем она и почему ей можно доверять.
- [ ] Документация и changelog обновлены.
